# Student Aid System Backend

学生家庭经济困难认定系统后端仓库。

- 后端：[student-aid-system-backend](https://github.com/Jelee0145/student-aid-system-backend)
- 配套前端：[student-aid-system-fronten](https://github.com/Jelee0145/student-aid-system-fronten)

## 项目目标与当前状态

本项目面向学生家庭经济困难认定与材料审核，旨在规范申请、审核及结果管理流程，支持前后端分工协作。

**当前处于仓库初始化阶段：仅提供项目说明和分支约定，尚未提交业务代码。** 下文业务能力是待确认、待实现的规划，不代表已经可用。具体角色、认定标准、审批层级及验收规则由产品与项目负责人确认后补充。

## 业务范围（规划）

- 学生提交家庭经济情况及认定申请，上传所需证明材料。
- 审核人员查看申请与材料，记录审核意见，并支持补正或退回。
- 按最终确认的认定标准和流程管理认定结果。
- 提供申请进度、结果查询及必要的统计管理能力。
- 对关键操作保留审计记录，按角色与数据范围控制访问权限。

建议先完成“提交申请 → 材料审核 → 补正/审核结果 → 学生查询”的最小闭环，再扩展其他能力。审核角色、状态转换、材料清单、公示与导出规则需通过需求评审确定。

## 分支与协作规范

两个仓库使用相同的长期分支：

| 分支 | 用途 | 合并要求 |
| --- | --- | --- |
| `dev` | 日常开发集成与前后端联调 | 功能分支通过 Pull Request 合并 |
| `test` | 测试验收版本 | 从 `dev` 提交 PR，完成联调后进入测试 |
| `prod` | 已验收的生产发布基线 | 从 `test` 提交 PR，测试通过并获发布批准后合并 |

流程：`feature/* 或 fix/* → dev → test → prod`。

- 从最新 `dev` 创建短期分支，如 `feature/application`、`fix/review-status`、`chore/deployment`。
- 一个 PR 聚焦一个功能或修复，说明改动、关联需求、验证结果以及配置/数据变更。
- 日常开发通过 PR 合并到长期分支；合并由指定的仓库维护人与项目经理负责审核。具体人员名单待维护者配置。
- 生产紧急修复从 `prod` 建立 `hotfix/*`，通过 PR 审核发布后，将修复同步回 `test` 和 `dev`。
- 生产发布使用版本标签，如 `v0.1.0`，并记录前端、后端各自的标签或提交 SHA，保证配套版本可追踪。
- `main` 保留为仓库初始化入口；日常集成、测试和发布按上述三个分支执行。默认分支调整由维护者另行配置。

开始开发示例：

```bash
git fetch origin
git switch dev
git pull --ff-only origin dev
git switch -c feature/application
# 完成开发和本地验证后
git add <本次改动的文件>
git commit -m "feat: add application flow"
git push -u origin feature/application
```

随后在 GitHub 创建目标为 `dev` 的 PR。

> 本文规定的是团队协作流程。分支保护、必需审批、CI 状态检查和成员权限需要在 GitHub 单独配置，README 本身不会强制执行。

## 环境与发布约定

至少区分开发（dev）、测试（test）、正式（prod）三套运行环境：

- 开发环境供开发人员自测和联调；自测通过后进入测试环境。
- 测试环境供测试人员验收；测试通过后才允许发布到正式环境。
- 各环境使用独立的数据库实例，避免开发或测试操作影响正式数据。
- 环境配置、文件存储和访问凭据分别管理；测试优先使用虚构或脱敏数据。
- 分支存在不等于环境已部署；每个环境需要独立的部署配置及验收记录。
- CI/CD 工具待团队确认，可选 Jenkins 或其他工具。规划流程为：代码检查 → 构建/测试 → 生成制品 → 部署对应环境 → 验证。
- 生产发布需记录版本、变更说明、验证结果以及回滚方案；涉及数据库变更时同时提供迁移与恢复说明。

**当前未接入自动化构建、环境部署或 AI 代码审查。** 配置完成后应在本文件补充实际入口和运行说明。

## 安全与数据约定

- 不提交真实学生申请材料、身份证明、家庭经济信息或其他敏感数据。
- 不提交数据库密码、令牌、私钥、真实环境配置或云服务密钥。
- 配置模板仅使用占位值；真实值通过环境变量、服务器配置或 CI/CD 的秘密管理机制注入。
- 上传材料的访问应经过身份与权限校验；日志中应避免记录材料内容和完整个人信息。
- 服务端负责权限与审核规则校验，前端按钮显示不能替代访问控制。

## 后端职责（规划）

- 提供身份认证、角色权限与数据范围校验。
- 实现申请提交、材料管理、审核流转及结果查询接口。
- 维护认定规则、审核状态及操作审计，确保状态流转可追踪。
- 提供数据库迁移、接口文档与必要的统计查询能力。
- 对提交、审核等关键操作处理重复请求与并发冲突。

前后端联调前，应约定身份凭据、接口路径、字段类型、申请状态、错误码、分页规则、上传限制和时间格式。接口或数据模型变更需同步告知前端，并注明兼容性影响。

## 本地运行与构建

仓库尚无应用源码、依赖声明、数据库脚本或启动配置，因此目前没有可执行的服务启动命令。

技术栈及版本（包括语言、框架、构建工具和数据库）待后端团队确认。提交项目骨架后，补充以下信息：

1. 开发环境依赖及精确版本。
2. 依赖安装、数据库初始化/迁移命令。
3. 环境配置模板与本地开发配置方法。
4. 启动命令、服务端口和接口文档地址。
5. 测试、构建命令及构建产物位置。

Dockerfile 的运行时、构建命令、产物路径和启动参数由后端与运维共同确认；环境编排和发布配置由维护者统一协调。
